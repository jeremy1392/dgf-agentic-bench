\section{DGF-Bench: measured review performance on 300 synthetic projects}
\label{sec:benchmark}

\subsection{Question, population, and information available to the agents}

This experiment asks whether an AI agent can apply a declared governance policy, identify the
required findings and actions, cite observed evidence, respect its authority, and carry a review
through a connected route. It measures review decisions and proposed actions, not implementation
of remediation or changes in human workload. It is distinct from the prospective enterprise and
factorial studies in Section~\ref{sec:testing}.

Three practical questions organize the analysis: (1) does the model reach the disposition
required by the rules, (2) does it produce all the supporting work needed for a valid review,
and (3) does that reliability survive a sequence of reviews at an acceptable API cost?
The unit called a \emph{case} or \emph{dossier} is one generated project; a \emph{gate} is one
checkpoint on its route. Three models reviewing the same 300 projects produces 900 planned
model--case runs, not 900 independent business projects.

The dataset contains 300 fictional projects: 100 Buy, 100 Integrate, and 100 Build cases.
Buy and Integrate contain six gate occurrences each, and Build contains five, for 1,700 occurrences
per model and 5,100 planned observations across three models. Cases were generated before these
evaluations at difficulty setting 4, with sampling conditioned to improve decision coverage.
The setting controls candidate fault patterns, including address overlap, supplier sanctions,
and mandatory-criterion failures; it is not an empirically calibrated measure of task difficulty.
Facts are rejection-sampled to balance base General dispositions and approximately balance feasible
specialist dispositions while preserving route consistency. This conditioning changes the raw
generator frequencies; no comparison across difficulty settings is reported.
Project context, owners, budgets, data classifications, technical architectures, documents, and
simulated system records derive from canonical case facts. Documents can be missing, stale, or
inconsistent. Specialist reviews precede a final General review; the routes are examples rather
than a universal enterprise standard.

The agent receives gate objectives, a structured output contract, an explicit decision policy,
and tools to read allowed evidence and query the synthetic environment. In particular, the policy
includes executable rule definitions and identifies an authoritative structured
\texttt{REVIEW\_FACTS} snapshot. The evaluator-only reference file is inaccessible through the
agent's tools. This is nevertheless a strongly scaffolded test of policy application: the agent
need not discover the rules or reconstruct every decision-relevant fact from unstructured documents.
Architecture images are available under the vision setting; image availability is not evidence
that image interpretation was necessary for success. These design choices limit claims about
expert reasoning on independently collected enterprise dossiers.

The dataset audit reports 300 distinct project identifiers, architecture signatures, and complete
decision-fact signatures, but only 267 distinct whole-case finding patterns. Gate-specific relevant
fact signatures include 142 of 200 Compliance cases and 241 of 300 Security cases. All rules
applicable to the selected phases are covered according to the generator's audit. Phase-adjusted
normalized decision entropy ranges from 0.9971 to 1.0000. Balanced labels improve coverage, but
do not estimate enterprise prevalence or establish independent business validity.

\subsection{What is generated, and what the model actually does}
\label{sec:bench-walkthrough}

The case generator is a program using seeded facts, rules, and document templates. The AI model
under evaluation is the reviewer, not the author of the fictional need or architecture. A Buy
scenario represents acquiring a solution; Integrate represents connecting existing systems;
Build represents developing a new project. Those scenarios are given budgets, users, owners,
dates, data classifications, and technical constraints. A generated name is a scenario label,
not an independently elicited customer requirement.

\begin{enumerate}
\item \textbf{Construct the project facts.} The program fixes what is true in the synthetic
case, such as the requested budget, whether a supplier has supplied a document, or whether a
restore test succeeded. Decision-coverage sampling produces cases with different required outcomes.
\item \textbf{Generate the design and dossier.} The same case drives an architecture diagram,
project charter, gate review requests, and evidence files. A reviewer may receive a technical
design, network/data-flow tables, contract records, security evidence, or readiness tests,
depending on the gate (Table~\ref{tab:bench-dossier}). Some presented evidence is incomplete or stale.
\item \textbf{Start a gate review.} The harness supplies the project context, gate and phase,
applicable policy, permitted evidence and tools, and the answer schema. The model decides which
allowed records to inspect. It can list and read evidence, query simulated systems, request
information, and inspect existing authorization mandates.
\item \textbf{Submit a decision.} The model returns a disposition, finding identifiers,
proposed actions, evidence references and supporting excerpts, an authorization indicator, and
a rationale. A typed submission is recorded. Producing a syntactically valid record alone does
not satisfy the substantive score.
\item \textbf{Continue the route.} In the tested \texttt{agent} mode, the harness passes actual
upstream model reviews to later checkpoints. The final General review consolidates specialist
opinions and its own checks. The tested routes are listed in Table~\ref{tab:bench-sequences}.
\item \textbf{Evaluate and retain the trace.} A deterministic evaluator compares the submitted
record and observed tool events with the reference. It records component scores, full gate and
route success, critical misses, false approvals, provider failures, and usage. It is not another
LLM judge. Failed or incorrect decisions are retained; infrastructure exclusions are reported.
\end{enumerate}

\subsection{Protocol, completion, and outcomes}

Table~\ref{tab:bench-models} identifies the three tested endpoints. Each receives the same
case population, policy, tool interface, and task limits; no model is trained or fine-tuned by
this experiment. The comparison concerns these deployed endpoints under the recorded conditions,
not different implementations of a human review process. Configuration was temperature
0, vision \texttt{auto}, agent-produced handoffs, at most 20 turns and 40 tool calls per gate,
and 8,192 output tokens per turn. Gates remained sequential within a project. The last resume
used 12 workers, four per model, and a USD~110 cost cap; an earlier invocation used six workers
and a USD~65 cap. Data collection spanned 22--23 September 2026. Resumption retained completed
cases and valid gate checkpoints. Historical provider/key-limit failures remain in the released
traces. The 78.73-minute elapsed time in the last run statistics describes that resume only.

Of 900 planned model--case runs, 899 are evaluable: 300 for DeepSeek, 299 for Gemini, and 300
for Luna. Gemini case \nolinkurl{DGF-INT-035128_integrate} failed at its first IT gate with
a provider generation error (\texttt{finish\_reason=error}); it is excluded as an infrastructure failure. Thus 5,094 of 5,100
planned gates are evaluable, with all expected gates attempted in the evaluable cases. There
are no recorded final agent-protocol failures or model-identifier mismatches. Provider-reported
identity is not an independent audit of underlying weights. DeepSeek was served by multiple
OpenRouter providers; Gemini and Luna were recorded through Google AI Studio and OpenAI.

Scoring uses \texttt{DGF-decision-v8.2-authorized-review}. A gate succeeds strictly only if its
disposition, finding set, action set, evidence provenance, and authorization indicator all satisfy
the reference. Findings and actions require F1 equal to one. Evidence requires an observed
reference and exact excerpts supporting the relevant field/value tokens. This is lexical
provenance checking, not independent verification of arbitrary reasoning. Authorized conditional
approvals can change the effective reference disposition; the evaluator verifies the mandate
and recorded action. General combines effective reference opinions, so an upstream error can
also cause a downstream failure. Complete-route success requires every gate to succeed strictly;
it does not mean that remediation was executed.

For model $m$, let $s_{mcg}$ be one when gate $g$ of case $c$ passes every component, and
zero otherwise. The two principal rates are
\[
\mathrm{GateCSR}_m=\frac{\sum_c\sum_{g\in G_c}s_{mcg}}{\sum_c |G_c|},
\qquad
\mathrm{RouteSuccess}_m=\frac{\sum_c\prod_{g\in G_c}s_{mcg}}{|C_m|},
\]
where $C_m$ contains the evaluable cases and $G_c$ their expected gates. This gate rate is
weighted by gate count: a six-gate route contributes six observations and a five-gate route
contributes five. A model passing four gates of a five-gate case has 80\% gate success for that
case but zero complete-route success. Decision-only accuracy checks just the submitted
disposition. A critical miss is an omitted reference finding classified as critical; a false
approval is \texttt{GO} or \texttt{GO\_WITH\_RESERVATIONS} when the effective reference requires
rework, suspension, or refusal.

Gate confidence intervals use a route-stratified bootstrap of whole cases, preserving dependence
between a project's gates (2,000 draws, seed 81931; a case-count Wilson fallback handles degenerate
intervals). Route intervals use Wilson bounds. Pairwise differences use the same 299 cases for
all models, resampled together within routes (10,000 draws, NumPy seed 81931). These are descriptive
intervals conditional on the synthetic sampling design. No preregistered analysis or independently
adjudicated ground truth is claimed. The original 300-case study contains one trajectory per
model and case; the subsequent repeated-trajectory study in Section~\ref{sec:bench-followup}
addresses variability on a separately identified 15-case subset.

\subsection{Evidence failures, unsafe approvals, and cost}

Disposition accuracy alone is 100\% for Gemini, 98.12\% for Luna, and 95.24\% for DeepSeek.
All 85 Gemini strict failures concern evidence conformity; findings, actions, dispositions, and
authorization indicators match the reference. Evidence is the sole failing component in 221 of
284 Luna failures and 338 of 439 DeepSeek failures. Invalid excerpts and missing or unobserved
references are grouped by these diagnostics; not all are harmless formatting defects. The
post-hoc structural sensitivity and source audit below now separate some of these causes.
Their alternative endpoint is explicitly labelled and does not replace the original strict
score or claim to measure general semantic entailment.

\paragraph{A recorded example of a correct decision with a failed proof.}
In \nolinkurl{DGF-BLD-035201_build}, Gemini reads the Architecture facts: an API gateway is
required but absent, and measured latency is 55~ms against a 20~ms target. It correctly names
\texttt{ARCH-API-001} and \texttt{ARCH-PERF-001}, proposes adding the gateway and remediating
latency, and submits \texttt{REWORK}. Two attempted conditional approvals are rejected by the
tool: one omits an open finding and the other includes a finding ineligible for risk acceptance.
The submitted refusal to proceed is consistent with those restrictions.

The gateway excerpt reverses two fields. It places \nolinkurl{api_gateway_present} before
\nolinkurl{api_gateway_required}; the observed record has the reverse order. The values are
correct but the excerpt is not an exact observed sequence. Evidence fidelity is 0.5 for the
two findings, so strict success is zero while disposition, finding, action, and authorization
scores are all one. The weighted component score is 0.95. This selected trace explains exactly
how a substantively correct review can fail this benchmark's evidence contract. The original
strict outcome is retained; the following sensitivity reports the effect of accepting exact
field/value equivalence separately.

DeepSeek records one critical finding miss and one false approval, both in the Architecture
review of \texttt{DGF-INT-035136\_integrate}. An address overlap required \texttt{NO\_GO}; at
forced finalization, the model submitted \texttt{GO} with an empty finding set, no evidence, and
a ``placeholder'' rationale. The response passed the submission schema but failed the substantive
score. This observation combines decision quality with the ability to finalize under resource limits.

Luna records three critical misses and one false approval. In case
\texttt{DGF-INT-035197\_integrate}, its Legal review approved a dossier with a missing DPA,
while its own rationale said that \texttt{REWORK} was required. The other critical misses concern
private endpoints in Security and an upstream \texttt{NO\_GO} in General. The latter can include
error propagation and should not be interpreted as an independent new safety event. Gemini has
no observed critical miss or false approval in its evaluable runs; this does not establish zero
risk. Recorded truncated-response counts are 2 for DeepSeek, 14 for Gemini, and 0 for Luna,
without implying that these counts equal incomplete cases.

The usage ledgers sum to USD~87.015829172, agreeing with the cumulative budget counter.
Gemini accounts for USD~71.88, DeepSeek USD~10.09, and Luna USD~5.05, including recorded retries
and failures. Approximate cost per evaluated dossier is USD~0.240, 0.034, and 0.017, respectively.
Luna therefore combines a higher overall strict score with lower recorded cost than DeepSeek
in this execution. Costs depend on provider routing, caching, price, and retry history; they are
not a labor-cost comparison or a permanent pricing claim.

\subsection{Completed controls, evidence audits, and repeated trajectories}
\label{sec:bench-followup}

The following additions distinguish completed analyses from development work and proposed
experiments. They preserve every original score above. Detailed methods and machine-readable
results accompany the focused companion manuscript,
\href{https://github.com/jeremy1392/dgf-agentic-bench/blob/main/paper2/From_Governance_Reviews_to_Task_Substitution.pdf}{\emph{DGF-Bench: Rule Application and Evidence Reliability in Synthetic Governance Reviews}}.
The companion analyzes the same original population and the completed repetitions; it is not
an additional independent 300-project replication.

\paragraph{An executable-rule control.}
A deterministic comparator applies the policy already supplied to agents to the public factual
snapshots. Generation blocks hidden-reference reads and is separated from scoring. It passes
1,700/1,700 gates and 300/300 routes, with no model API cost. It retains base decisions rather
than requesting conditional approvals and may cite complete observed snapshots under the
original unrestricted excerpt contract. This establishes that the scaffolded task is solvable
without a language model. High LLM decision accuracy therefore demonstrates an ability to
apply these rules through the interface; it does not establish added accuracy over the rule
control or the ability to recover the necessary inputs from arbitrary documents.

\paragraph{Structural sensitivity on all three models.}
All 690 originally evidence-failed gates were audited. The alternative endpoint retains
original lexical successes and additionally accepts exact field/value subsets within a single
observed object, ignoring field order and equivalent numeric serialization. Required source
reads, citations, relevance to a rule field, and all other score components remain unchanged;
cross-object joins are not promoted. Table~\ref{tab:bench-followup-original} shows the paired
results. These are post-hoc provenance sensitivities, not a new semantic score: an observed
value need not supply every premise of an argument. In particular, failure to parse an
excerpt as one JSON object does not show that its factual claims are false.

\subsection{Interpretation and reproducibility boundary}

The empirical conclusions are concrete. \textbf{First}, Gemini has the highest overall strict
review success under this protocol, including in the paired comparison. \textbf{Second}, a
project-level requirement amplifies remaining strict-contract defects: 94.98\% gate success leaves
69 of Gemini's 299 evaluable projects without a completely conforming route; the separately
labelled structural endpoint reduces that count to 15. \textbf{Third}, evidence
conformity is the sole failing component in all Gemini strict failures and most failures of the
other models. \textbf{Fourth}, Luna achieves higher overall strict success than DeepSeek at
approximately half the recorded cost, while both retain substantive errors. Finally, the zero
observed false approvals for Gemini are an observation about this sample, not a safety guarantee.

For an FDE, these results identify implementation work to investigate: preserving observed evidence
through structured submissions, checking agreement between a rationale and its typed decision,
handling turn-limit finalization, and inspecting downstream consequences. These are proposed
engineering responses to observed failure modes. The completed diagnostics and repetitions above
clarify those modes; the development prototypes have not yet demonstrated a model-performance gain.

The experiment demonstrates strong review performance under an explicit rule system: Gemini
satisfies every strict requirement on 94.98\% of evaluable gates and on every gate of 76.92\%
of evaluable project routes. This is empirical support for the technical prospect of substantial
automation of the review tasks represented here. The rule control also completes this fully
specified task, so the observed LLM capability is not an accuracy advantage over deterministic
software. If comparable performance transfers to operational
settings, these tasks could require less human effort and fewer staff, including substitution for

The published release preserves all files of the recorded run and its dataset, including old
failed attempts, the original partial exports, and the final analysis. Only the final analysis
tables describe the 899 evaluable runs. Frozen benchmark sources reproduce the recorded source
fingerprint; the repository's evolving default branch is not substituted for them. Five targeted
offline rescoring checks reproduced the saved gate scores exactly, including all cases with critical
misses, and all 899 score files passed internal count consistency checks. These checks establish
reproducibility of this evaluator, not independent validation of its governance judgments.

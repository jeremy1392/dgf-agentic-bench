\section{The FDE implementation: engineering the whole workflow}
\label{sec:fde}

Forward deployed engineers (FDEs) work alongside organizations to turn software capabilities
into deployed systems; embedded implementation is explicit in the role described by
\citet{palantirfde2026}. Here the role has a concrete purpose: construct the information,
policy, evidence, and authorization interfaces that let an accepted review be completed without
requiring a person to reconstruct it. The job title itself does not establish an advantage.

Figure~\ref{fig:implementation} separates responsibilities. Agents can investigate a dossier,
extract candidate facts, interpret narrative material, and propose findings. Where policies
are executable, a deterministic service evaluates them. Evidence services attach copied source
values and locations rather than asking a model to reproduce quotations. Mandate checks govern
commitments. The system escalates cases for which its evidence or delegated scope is inadequate.
These are proposed deployment components, not a claim that this complete architecture was
evaluated by the current benchmark.

The FDE's work has four measurable deliverables. First, connect the required facts to accessible
sources and demonstrate that the source set is sufficient for the declared task. Second, encode
policy versions and mandates with the responsible owners, including the treatment of exceptions.
Third, make the accepted record usable by the next gate without re-reading and re-verifying the
whole dossier. Fourth, measure failures and human hours across the process, including the FDE's
own recurring work. Policy formalization and initial integration are transition investments;
continued adaptation is an operating burden. Neither disappears because a supplier performs it.

These deliverables explain the proposed DGF-first strategy. An FDE implementing an enterprise
agent encounters project governance during deployment. The interfaces built to navigate it can
also become interfaces through which its reviews execute. Policy ownership, evidence access,
and repeated decision formats create reusable engineering opportunities. The claim is a plausible
sequence of deployment work, not evidence that DGF must precede every business application.
High-volume operational processes may justify automation earlier.

Designing common interfaces across gates matters even when rollout is incremental. Consider an
Architecture review accepting a design only if a private endpoint is added. Security must
receive both the condition and whether it has been fulfilled; receiving an unqualified approval
would change the contract. A system that preserves such state can reduce repeated interpretation.
A system that drops it can create new human verification work. Whole-route outcomes and the
shared labor account test these alternatives; adding local automation percentages does not.

In deployment, the decisive object is therefore the \emph{accepted task}, not the number of
generated reports. Routine cases can have no required human execution while rare cases retain
specialist review. If every case requires a lengthy signature or reconstruction, that review
appears in $h_R$ and can erase the gain. Conversely, keeping an accountable owner does not by
itself imply keeping the same number of people executing each review.
